# 定制门业企业经营分析系统

[![CI](https://github.com/5x486/door-manufacturer-analytics/actions/workflows/ci.yml/badge.svg)](https://github.com/5x486/door-manufacturer-analytics/actions/workflows/ci.yml)

> 30 秒速览版与截图见 [README_求职版.md](README_求职版.md)。

一套面向小型定制门厂的经营分析系统：把「8 张 CSV + 3 本 notebook + 一个 Streamlit 看板」的离线原型，重构成 Django + MySQL + DRF + 测试 + 部署配置的完整系统。数据全部由程序模拟生成，业务背景为浙江嘉兴桐乡一家 2023 年起步的小型定制门厂（1 个工厂展厅 + 抖音短视频接单 + 老客户转介 + 装企合作），主营铜门、不锈钢门、不锈钢铜门、铸铝门、甲级防盗门、防火门 6 大品类。

数据区间 2023-01-01 至 2026-07-31。

## 四、数据与口径

### 四层表结构

| 层 | 表数 | 内容 | 设计意图 |
|---|---|---|---|
| 主数据 | 7 | 产品、产品成本标准、门店、业务员、员工、客户、竞品对标价 | 描述「谁、卖什么」，被事实表引用，改动频率低 |
| 业务事实 | 9 | 订单、订单明细、明细成本、付款、合同账期与应收、售后、交付阶段、销售目标、工时 | 描述「发生了什么」，是最细粒度的事实层，只追加不修改 |
| 分析治理 | 13 | 指标口径、指标拆解、数据版本、8 张 dws_* 预聚合、模型版本、评分结果 | 描述「怎么算、算过没有」，把口径与加速层一起治理 |
| 数据质量 | 3 | 规则、批次、结果 | 描述「这份数据可不可信」 |
| 系统 | 1 | 自定义用户 | 账号与角色 |

### 指标口径入库的做法

56 条指标口径不是写在文档里的表，而是数据库里的实体：每条口径带唯一编码（如 `M_REV_001`）、中文名、业务域、公式、单位、粒度、责任人、排除规则和版本号。另有 44 条指标拆解关系，构成指标树（例如营收拆成订单量乘客单价，再往下拆新客数与复购率）。

这样做换来三件事：

1. 口径有编号，讨论时说的是「M_REV_001 怎么算」，不是「你说的那个营收是指哪个」。
2. 口径有版本，改口径时旧结论仍可追溯，历史报表不会因为口径静默变化而前后矛盾。
3. 接口响应的 `meta.metric_definitions` 直接带上口径编码，前端 KPI 卡鼠标悬停就能看到「这个数怎么算的」，口径文档嵌进了产品。

### 口径只在服务层算一次

视图、页面模板、API 接口都不允许自己写聚合公式，一律调用 `apps/analytics/services` 与 `selectors`。这条约束有直接的工程收益：页面与 API 的同一个指标永远相等，改口径只需要改一处，测试也只需要盯一处。

## 五、数据质量

25 条规则分五类，规则元数据与规则实现分开：`rules.py` 写清「这条规则是什么、为什么要有它」，`checks.py` 负责怎么算。规则本身也入库，供页面展示与审计追溯。

| 类别 | 规则数 | 抓什么 |
|---|---|---|
| 主键唯一 | 5 | 订单号、明细业务键、付款流水号、客户编码、产品编码重复 |
| 外键完整 | 5 | 订单到客户、明细到订单、明细到产品、付款到订单、售后到订单的悬空引用 |
| 金额对账 | 4 | 终价公式自洽、明细合计与订单总额一致、成本非负、付款金额方向正确 |
| 日期合理 | 4 | 交付不早于下单、付款不早于下单、无超出数据截止日的未来日期、交付阶段不倒挂 |
| 业务合理 | 7 | 取消单无交付、有效订单必有明细、准时率区间、毛利率区间、售后率阈值、售后品类值域、明细数量为正 |

每条规则带 `severity`：`error` 级破坏口径正确性（主键重复、外键悬空、金额对不上），`warning` 级是业务合理性存疑（准时率越界、售后率偏高）。阈值用「异常行数」而不是「异常比例」，因为「有 3 张订单金额对不上」比「异常率 0.12%」更好沟通，也不会因为数据量翻倍而自动放宽标准。

最近一次校验结果：25 条规则，通过 24、警告 1、失败 0，耗时约 500 毫秒。结果落到 `dq_run` 与 `dq_result` 两张表，所以能看到「上周还好，这周主键重复了」这样的趋势对比，异常样本主键也一并落库，出问题时不用重跑脚本就能定位到具体哪几行。

`error` 级失败时 `check_quality` 返回非 0，可以直接进 CI，让数据问题阻断发布而不是在报表上悄悄放大。

## 六、模型

notebook 里的模型全部搬上线，并且每一项都与基线对比。如果一个模型打不过规则基线，那它就不该上线。

| 模型 | 指标 | 基线与对比结论 |
|---|---|---|
| KMeans 客户分群 | 与规则 RFM 分群交叉验证，Cramer's V 0.47 | 中等强度一致：说明聚类结果与业务可解释的分群规则方向一致，权重取用规则口径而不是黑箱簇 |
| 复购预测 | AUC 0.68 | 优于随机基线 0.50，也优于单一「最近一次下单距今」规则特征 |
| LTV 回归 | R²（对数尺度）0.38 | 门业是低频高客单生意，LTV 本身波动大，0.38 属于可用区间；因此页面展示的是分位区间而不是单点预测值 |
| 订单量预测 | MAPE 15% | 走前向验证（walk-forward），优于「上月等于本月」的朴素基线 |

模型产物用 joblib 持久化，`ModelVersion` 表记录版本、算法、训练区间、特征清单与评估指标；`ScoringResult` 表记录每个订单或客户的评分、所用模型版本与关键贡献因子。所以「模型在线」页面能回答三个问题：这个结论来自哪个模型版本、它的历史表现如何、某一条评分为什么是这个值。

KMeans 这一项特别值得说明：它没有直接用于业务分层。聚类结果只用来交叉验证规则 RFM 分群是否合理，最终落地的分层口径仍然是可解释的规则。这是「模型辅助结论」而不是「模型替代结论」。

## 七、前端设计系统

界面按「克制的产品页」重做，所有视觉决策集中在 `static/css/design-system.css`，模板里不写零散样式。

| 项 | 取值 |
|---|---|
| 主题 | 浅色为主 + 近黑侧栏，深色模式可手动切换，选择记忆在本地 localStorage |
| 强调色 | 只有一个：`#2C7A7B` 不锈钢色，呼应不锈钢门这项主营品类 |
| 文字强调色 | `#226466`，比强调色更深，用于保证小字号的 WCAG AA 对比度 |
| 密度 | 中等（卡片留白与信息密度取平衡，一屏内看清一组指标） |
| 导航 | 固定左侧栏 + 5 组分组 + 顶部面包屑 |
| 图标 | 24 个内联 SVG（`templates/partials/_icon.html`），全站无 emoji 图标 |
| 图表 | 从 CSS 变量读取主题，切主题图表自动跟随；细致标注风（轴单位、图例、数值直标、参考线），去掉默认边框与阴影 |
| 动效 | 卡片悬停抬升、图表入场、KPI 数字滚动、抽屉滑出；尊重 `prefers-reduced-motion` |

设计 token 全部是 CSS 变量：色板、8 档字号、7 档间距、4 档圆角、3 级阴影、动效曲线，深色模式整套覆盖。切主题时只换一层变量，组件代码不需要任何条件分支。

### 动效层：让页面切换像原生应用

界面之上还有一层独立的动效与材质：`static/css/motion-layer.css` 与 `static/js/motion.js`。它只叠加、不修改设计系统本体，整份删掉也不影响功能与布局。

| 动效 | 做法 | 为什么这么做 |
|---|---|---|
| 跨页转场 | `@view-transition` 跨文档 View Transitions，侧栏与顶栏单独命名后保持不动，内容区淡入并上浮 12px | 换页不再是「白屏闪一下」，而是内容在原地替换；外壳不动，用户不会失去方向感 |
| 首屏编舞 | 标题、筛选条、KPI、卡片按 DOM 顺序逐级 52ms 入场，滚动到视口的区块再依次唤起 | 一次性全部出现等于没有重点；错开 50ms 就能读出「先看标题、再看卡片」的顺序 |
| 顶栏浮起 | 滚动超过 8px 后加毛玻璃、发丝线与一层极淡的投影 | 让人感觉到内容在导航下面滑过，而不是导航跟着一起走 |
| 指针光晕 | 鼠标位置写入卡片的 `--mx / --my`，CSS 用径向渐变画一层柔光 | 比整卡变色更克制，也让「这块可以交互」这件事有反馈 |
| 图表绘制 | ECharts 绘制时长 900ms，`cubicOut` 长尾曲线 | 看得到笔尖画过去的过程，数字才像「算出来的」而不是「本来就有的」 |
| 数字滚动 | `easeOutExpo`，按卡片顺序递延 60ms | 前三帧冲到九成、最后慢慢落定，是苹果官网数字的手感 |

三条工程约束写进了实现里。第一，入场前的隐藏状态由 `<head>` 内联脚本在首帧之前加上，避免「先显示再消失」的闪烁；万一 `motion.js` 没跑起来，1.6 秒后的兜底会把内容全部显示，宁可没有动画也不能丢内容。第二，走转场过来的页面不再重播入场，否则转场快照会停在「尚未淡入」的状态，看起来像闪白。第三，所有动画只动 `opacity / transform / translate`，不动 `top / left / width / height`，并且整套在 `prefers-reduced-motion` 下退化为瞬间到位。

### 为什么强调色只有一个

强调色的价值来自稀缺。当页面上有五种彩色，用户就无法从颜色判断哪一处是「现在该看的地方」。这个系统里颜色承担固定的语义：强调色标记可交互元素与关键数值，语义色只用于状态（成功、警告、失败），其余全部是灰阶。中文经营看板常见的做法是每个品类一个颜色，结果是图例比图还花，用户看完记不住任何一条结论。需要区分品类时，用同一强调色的明度梯度加数据直标，比换五套色系更可读。

### 为什么文字色要比强调色更深

`#2C7A7B` 与白底的对比度约 3.9:1，达到 WCAG AA 对大字号（18pt 以上或 14pt 加粗）的要求，但达不到对正文小字号的 4.5:1。所以同一个颜色要分两个用途：作为图形元素、边框、图表主色时用 `#2C7A7B`；作为小字号文字（KPI 单位、表头、链接、脚注）时降到 `#226466`，对比度约 5.9:1，满足 AA 正文标准。深色模式下这套变量整体重算，取的是「在深色背景上重新达到 AA」的对应值，而不是把浅色值调亮。

把这条写进设计规范，是因为它是那种「看起来只是浅一点深一点」，但直接决定表格能不能被看清、投影仪上能不能被读出来的细节。「页面冒烟 + 设计规范回归」测试里专门有两条用例守住无 emoji 与无破折号，原因同一：这类退化一旦发生，没有人会当成 bug 报上来。

### Docker 与 CI

- `Dockerfile`：`python:3.12-slim` 打底，非 root 用户运行，先装依赖再拷代码以命中缓存，健康检查打应用自身根路径。
- `deploy/docker-compose.yml`：`db`（MySQL 8.0，utf8mb4，命名卷持久化，健康检查就绪后 web 才启动）+ `web`（迁移 + 收集静态文件 + gunicorn 3 worker）。
- `deploy/nginx.conf`：静态文件与媒体文件由 nginx 直出，应用只处理动态请求。
- CI 三个 job：`lint` 做 Django 系统检查与迁移一致性检查（防止有人改了模型忘记生成迁移），`test` 在 MySQL 服务容器上跑测试并卡覆盖率门槛，`data-quality` 端到端跑一次灌数与质检。
- 测试环境用 SQLite 内存库，因为被测重点是口径与业务逻辑而不是数据库方言；与 SQL 方言强相关的用例用 `@pytest.mark.integration` 标记，在 CI 里切回 MySQL 跑。

需要说明：「Docker 与 nginx 配置已提供，但未在公网环境实测」。详见 `docs/DEPLOY.md`。

## 十、改造演进

### 改造前是什么样

第一版是一个原型：8 张 CSV 加 3 本 notebook 加一个 560 行的 Streamlit 看板。分析内容本身是扎实的，随机种子固定、数字可自证，但形态上是一堆离线脚本加一个单文件看板，不是系统。四个问题会被面试官当场问住：

1. 没有数据库、没有 ORM、没有服务分层，被问「数据怎么进库的」答不上来。
2. 全篇围绕营收展开，没有成本、毛利、边际贡献的视角，被问「所以赚了多少」答不上来。
3. 模型只活在 notebook 里，跑完就结束，没有持久化、没有版本、没有在线评分。
4. 没有版本控制、没有测试、没有部署配置，被问「线上怎么跑」答不上来。

### 这一版改了什么

把分析资产搬进一个真正的系统：33 张表的四层建模；指标口径下沉到服务层并入库；把清洗与质检改写成幂等的管理命令；新增成本毛利、客户 360、留存 cohort、回款账龄、人效与门店、决策模拟、数据质量、模型在线八个原本缺失的模块；前端按设计系统重做；补上四类测试、Docker Compose 与 CI。

旧版 Streamlit 原型保留在 `dashboard/app.py`，作为改造前后的对照：同一个问题在两套实现里怎么答，比只看最终版更能说明改了什么。

### 三条工程教训

**教训一：口径只能有一个来源，能算出来的就不要导入。** 早期订单表直接导入 CSV 里的 `final_amount`，而这个值是四舍五入的产物，与 `total_amount × (1 - discount) + freight` 存在分位差。结果是一条金额对账规则持续报警，而分析结论看起来完全正常，因为没有任何一个数字「明显错」。后来改成「能算出来的就不导入」，成交额只保留一个来源。同理，应收账龄曾经全部为 0，因为付款流水是按合同额生成的，直接按流水算应收会得出「所有单都结清、逾期 0 条」这种不可能的结论。这两个 bug 的共同点是：错误不会报错，只会让结论安静地错。

**教训二：横切逻辑的默认值必须是「缺则补」，不能是「无条件覆盖」。** 页面的横切出口无条件下发了一份 `metric_definitions` 默认值，把指标字典视图已经算好的结果覆盖成空列表，导致整页 500。修复只用了一行判断，但教训是关于横切设计的：一个为了「所有页面都有这个变量」而写的默认值，如果没有「缺则补」的语义，就会变成所有页面局部计算的静默杀手。

**教训三：框架约定与命名冲突要在建模阶段就避开。** 数据质量结果表的「检查对象」外键原本叫 `check`，撞上 Django 模型的内置方法 `Model.check()`，系统检查直接报 `models.E020`，项目起不来。同名问题还出现过一次：配置里 `base.py` 读 `DB_PORT` 而 `local.py` 读 `MYSQL_PORT`，两条变量名分叉，最终表现为一直连空端口并报 `10061`，排查方向完全被错误信息带偏到「数据库没启动」上。约定不一致的代价总是花在排查上，而不是花在写代码上。

另外两个值得记的坑：`only()` 与 `select_related` 不能作用于同一关联字段（共 4 处），以及 Django 模板的 `{{ x|default:未定义变量 }}` 在默认值本身未定义时会抛 KeyError 而不是静默回退，一个卡片的口径提示能拖垮整页。后者已经改成显式 if 分支回退。

## 十一、已知局限与下一步

### 局限

- **数据是模拟的。** 业务背景（品类结构、渠道方式、制造流程）依据企业公开信息校准，但交易数据是程序生成的。因此这份系统能证明「指标体系与工程实现是对的」，不能证明「这家公司真实经营如此」。所有金额与比率都应视为演示值。
- **未上公网。** 系统在本地与容器编排配置层面可运行，但没有部署到公网，没有实际域名的访问链接，也没有经过真实并发与安全扫描。
- **外生变量未建模。** 铜价、不锈钢价、房地产与装修市场景气度、季节性与政策因素都没有进入模型。因此订单量预测与 LTV 回归只适合内部分配资源，不适合对外承诺业绩。
- **单实例、批式。** 没有引入 Redis 与 Celery 队列做异步任务与定时刷新，预聚合重建是命令触发的；在当前数据量（十万行级）下够用，数据量再上一个量级需要重新设计。
- **权限模型简单。** 目前是两个角色（老板与只读访客），没有做行级权限，也没有做「业务员只看自己单子」这种真实团队场景。
- **测试覆盖有限。** 约 40 个用例覆盖了口径、质检、契约、幂等与页面冒烟，但没有覆盖并发、性能与前端交互。

### 下一步

1. 补齐截图与视觉复核，逐页检查 KPI 网格换行、图表标注是否拥挤、深色模式对比度与窄屏折叠。
2. 给四个核心接口加性能冒烟测试并把响应耗时写进文档，让「预聚合有没有用」有数字支撑。
3. 引入 Celery Beat 做每日定时刷新预聚合与评分，把目前的手动触发改成调度。
4. 做行级权限，让业务员只看自己的订单与客户。
5. 补充库存与在制品视角（物料、库存周转天数、呆滞料、缺料导致的逾期），把交付归因与供应链闭环。
6. 增加外生变量的敏感性维度（铜价、不锈钢价、装修景气度），让决策模拟的假设更完整。
