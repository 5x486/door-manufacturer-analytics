# 项目现状体检 + 改进路线图（v0 评估稿）

> 评估时间：2026-08-09 ｜ 评估范围：`door_analysis_project` 全部代码、数据、文档、notebook
> 评估方式：逐文件通读 + 用项目 venv 实际跑数复核文档中的每一个数字
> 用途：作为 Django 重构（第 1 项）与前端美化（第 2 项）的需求基线

## 一、一句话结论

**这是一个「文档远超工程」的项目。**

业务故事讲得很好、分析口径有想法、数字基本能自证，作为**数据分析岗**的作品集已经超过多数同届选手；
但它现在是一堆**离线脚本 + notebook + Streamlit 单文件原型**，不是一个"系统"。
一旦面试官问「数据怎么进库的」「线上怎么跑」「模型怎么上线」「多人怎么用」，现在**没有东西可以接**。

所以这次改造的正确方向不是"再画几个图"，而是：
**把已有分析资产装进一个真正的 Django 业务系统 → 用真正的数据库建模 → 用真正的 API/服务分层 → 用真正的产品级前端呈现 → 补上"钱"和"决策"这两个老板真正关心的视角。**

## 四、问题清单（按严重程度排序）

### 🔴 P0 · 会被面试官当场问住的结构性缺陷

1. **不是系统，是脚本集合**。没有数据库、没有 ORM、没有服务分层、没有 API、没有并发/权限概念。
   → 问「你这个数据怎么进库的？」「线上怎么跑？」「别人怎么用？」三个问题就会掉到地板上。

2. **完全没有"钱"的视角**。整个项目 100% 围绕营收（GMV）展开，**没有成本、没有毛利、没有边际贡献率**。
   门业是真有成本结构的：材料（铜价/不锈钢价）、人工、生产周期占款、运费、售后成本。
   数据里已经有价位、尺寸、非标系数、售后成本、运费、折扣——**只差一张成本表就能算出每个品类的毛利率**。
   HR/老板的原话一定是：「所以呢？赚了多少？」——现在答不上来。

3. **模型只活在 notebook 里**。KMeans / 复购预测 / LTV / 订单量预测，跑完就结束：没有模型持久化、没有特征工程沉淀、没有在线评分接口、没有预测 vs 实际的回看。
   → 这是"数据分析"和"数据应用"的分水岭，也是 Django 改造最能加分的点。

4. **零工程规范**：没有 git（我确认过，项目下没有 `.git`）、没有 `tests/`、没有 Docker、没有 CI、没有 `.env`、没有日志、没有异常处理、没有依赖锁文件。
   → 作品集要投的是"能进团队干活"的人，这一条会被扣得很重。

### 🟠 P1 · 功能缺口（决定项目"像不像真实系统"）

5. **缺少客户留存/复购的量化块**：有 RFM 快照，但没有 cohort 留存矩阵、没有复购间隔分布、没有流失预警名单。
6. **缺少员工/门店/区域效能**：`sales_reps.csv`（6 人）、`stores.csv`（3 个）在分析里几乎是摆设。业务员人效排行、门店对比是最典型的经营看板模块，现在**没有**。
7. **缺少交付履约的归因与预警**：只统计了准时率，没有"延期订单的风险特征分解"（哪些品类/尺寸/季节/金额段最容易延期）、没有超期订单明细与催办。
8. **没有决策模拟（What-if）**：全项目最缺的一块。老板问的是"钱投哪"，现在只能靠文字建议。
   应该做成：`渠道预算分配 → 预测增量收入`、`品类定价/折扣调整 → 毛利测算`。
9. **没有目标达成/预算对比**：没有"目标 vs 实际"的同比环比看板，这是经营看板的标配。
10. **付款/现金流视角缺失**：5,982 条付款记录几乎只用来做数据校验，没做「回款率、账期、应收未收、现金流」分析——工程/装企单最关心这个。
11. **售后只有频次没有成本**：`cost` 字段有，却没算售后成本占收入比、按品类归集的质量成本。
12. **没有客户 360 视图**：点一个客户看他的订单、付款、售后、RFM、预测价值——这是"系统"和"看板"最直观的区别。
13. **没有数据质量页面**：`check_data.py` 的结果没有可视化、没有历史记录、没有失败告警。

### 🟡 P2 · 代码与文档质量

14. `check_data.py` 用 `print` 输出、失败不 `exit(1)`，**无法进 CI**。
15. `clean_data.py` 的 `TODAY` 硬编码 `2026-08-09`，与生成脚本、看板三处重复定义，**改一处必漏两处**（这已经造成了下方的第 16 条）。
16. `README.md` 与数据字典存在口径/行数不一致（见第三节）；`README_求职版.md` 写"有效订单 2,232"、`resume_project_description.md` 又写"2,401 订单"，同一套数字两种说法。
17. `app.py` 售后率计算是真 bug：`as_cat` 按 `product_id` 分组（其实存的是品类），`dn_cat` 按 `dominant_category` 分组，**两边基准不同，算出的售后率口径是错的**；且退款类行未从分母剔除。
18. 侧边栏 `sel_cat` 为空时不走 `else`，`valid_cat = valid` 依赖真值判断，是**隐式耦合**——多选清空会静默改口径。
19. `dashboard/app.py` 单文件 560 行，CSS/数据/过滤/图表/文案全混在一起，**没有任何分层**。
20. `requirements.txt` 无版本上限策略、无 dev/prod 分离。

### 🟢 P3 · 呈现与体验

21. Streamlit 的样式是**逆向 hack 内部 DOM**（`[data-testid="stSegmentedControl"]` 等），Streamlit 一升级就崩；且**无法做移动端适配、无法分享深链、无法嵌进真实系统**。
22. 图表只有 hover 才有数，**没有数据标签、没有导出、没有下钻联动**。
23. 没有 loading 态、空态、错误态设计；没有面包屑与导航结构。
24. 没有登录/权限：真实经营数据（客户电话、地址就在 `customers.csv` 里）**任何人打开就能看**——这在真实公司是红线。

## 五、改进路线图（Django 版，按优先级分四期）

### 第一期 · 打地基（必做，决定"是不是系统"）
- Django 项目骨架 + 分 app：`core`（用户/权限/菜单）、`masterdata`（产品/门店/业务员/客户）、`sales`（订单/明细/付款）、`analytics`（指标服务层）、`ml`（模型注册与在线评分）、`datasource`（ETL 与数据质量）
- **真正用 ORM + 迁移建库**（SQLite 起步，Postgres 可切），把 8 张 CSV 表建模成有约束、有索引、有外键的真实表
- 把 `generate_data.py / clean_data.py / check_data.py` 改写成 **Django management commands**（`seed_demo` / `rebuild_dw` / `check_quality`），幂等可重跑
- 指标计算抽成 **service 层**（单一事实来源），看板不再各自算数
- 统一 `TODAY` 为配置项（`settings.DATA_AS_OF`），消灭三处硬编码
- 补：git 仓库、`.gitignore`、`.env.example`、`tests/`（pytest-django）、`Dockerfile` + `compose`、GitHub Actions CI

### 第二期 · 把分析变成功能（决定"能不能打动业务面"）
- **经营总览**：目标 vs 实际、同比环比、KPI 卡片 + 趋势 + 结论自动生成
- **增长与渠道**：留存/复购、渠道 ROI（预算 → 增量收入）
- **品类与定价**：帕累托 + **单位经济学（成本/毛利率）** + 折扣侵蚀监控
- **客户价值**：RFM 分群、**cohort 留存矩阵**、客户 360、流失预警名单
- **交付与售后**：延期归因、超期预警工单、**售后成本归集**
- **人效与门店**：业务员排行、门店对比、区域分布
- **现金流与回款**：回款率、账期分布、应收未收
- **决策模拟（What-if）**：渠道预算分配 → 预测收入；折扣/品类结构 → 毛利测算
- **数据质量页**：校验结果可视化 + 历史记录

### 第三期 · 模型上线（决定"技术纵深"）
- 模型训练产物落盘（joblib）+ 模型注册表（版本、训练时间、指标）
- 特征工程沉淀成可复用函数（防止训练/服务不一致）
- 在线评分接口：`POST /api/score/repurchase/`、`/api/score/ltv/`、`/api/forecast/orders/`
- 预测 vs 实际回看页（模型有没有用，一眼看出）
- 客户列表直接带"预测价值分"和"复购概率"排序

### 第四期 · 产品化（决定"看起来像不像成品"）
- 用**本地前端 skill** 重做界面：设计 token 化、组件化、响应式（含移动端）、深链与分享、加载/空/错误态、图表下钻联动
- DRF + OpenAPI 文档（`/api/docs`），让"这有 API"变成看得见的东西
- 登录/角色权限（老板/运营/业务员只能看自己数据）
- 部署：Docker Compose 一键起，可选公网可访问链接放进简历

## 六、改造后这个项目在简历上的说法（预演）

> **杭博门业经营分析系统**（Django / DRF / PostgreSQL / Pandas / scikit-learn / XGBoost / ECharts）
> 独立设计并实现**企业级经营分析系统**：以 Django + ORM 建模 8 张业务表（1,500 客户 / 2,401 订单 / 5,982 付款），
> 将数据生成、清洗、质量校验改造为**幂等 management command + ETL 分层**，指标计算下沉至 service 层统一口径；
> 基于 DRF 提供分析 API 与**模型在线评分接口**（复购预测 AUC 0.68 / LTV R² 0.38 / 订单量预测 MAPE 15%，均优于基线）；
> 前端实现 9 个分析视图与**决策模拟模块**；配套 pytest 测试、Docker Compose 与 CI 流水线，全链路可一键复现。

—— 和现在的描述比，多了「系统」「分层」「API」「模型上线」「测试/部署」五组关键词，这正是 HR 筛简历时在找的东西。

## 七、待确认的关键决策（决定我怎么动手）

1. 项目落在哪、要不要建 git（**改造前必须先有版本控制**）
2. 技术栈：Django 模板 + ECharts（纯 Django）／Django + DRF + 前端框架（前后端分离）
3. 数据库：SQLite 起步还是直接上 PostgreSQL
4. 目标岗位：偏数据分析 / 数据开发 / 数据产品——决定加点偏建模还是偏工程
5. 改造方式：原目录原地升级（保留 Streamlit 作对照）／新建 v2 工程
6. 功能优先级：上面第二期 9 个模块，你要哪几个
7. 是否补"钱"的视角（成本/毛利表）——**强烈建议加，这是最大增量**
8. 是否需要部署到公网（有链接的简历通过率明显更高）
